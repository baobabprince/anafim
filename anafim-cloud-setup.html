ענפים 2.0.1 — הקמת Google, כספת מוצפנת וסנכרון

מצב ההפצה: הקוד והגדרות מסד הנתונים מוכנים להגדרה. לא נוצר פרויקט ענן, לא הוכנסו פרטי חשבון אמיתיים ולא נבדקה התחברות חיה מול Google/Supabase של המפעיל. ללא ההגדרות הבאות, היישום מציג במפורש ״ענן לא הוגדר״ ונשאר מקומי.

המדריך הכללי והמלא, כולל קידוד GEDCOM, פיתוח, פריסה ופתרון תקלות, נמצא כעת ב־README.md. מדריך זה מתמקד בצעדי הענן.

מה נבחר

  • Supabase Auth עם ספק Google לזיהוי החשבון.
  • PostgreSQL ו־Storage פרטיים, עם RLS לכל משתמש.
  • הצפנה מקצה לקצה בדפדפן; שרת היישום אינו מחזיק מפתח פענוח גלוי.
  • Passkey עם הרחבת PRF לפתיחת המפתח. מזהה Google אינו סודי ואינו סיסמת הצפנה.
  • מפתח שחזור פרטי שנמסר רק למשתמש, עם אישור שמירה לפני יצירת גיבוי.

1. כתובת אתר קבועה

בחרו דומיין HTTPS קבוע. כתובת ה־RP של Passkey קשורה לשם המתחם: שינוי דומיין עשוי לדרוש את מפתח השחזור ורישום Passkey חדש. לפיתוח השתמשו ב־http://localhost:5173 ולא ב־file://. לכתובות IP כגון 127.0.0.1 עלולות להיות מגבלות WebAuthn.

תצוגת iframe מוגנת עשויה לחסום OAuth, Passkeys, הורדות או רשת. בצעו את ההפעלה בדפדפן מלא ובכתובת האתר עצמה.

2. פרויקט Supabase

  1. צרו פרויקט בחשבון שלכם ובחרו אזור נתונים מתאים.
  2. ב־SQL Editor הריצו את כל הקובץ supabase/migrations/202610180001_private_vault.sql כגורם המנהל את הפרויקט.
  3. ודאו שה־bucket בשם anafim-vaults הוא פרטי, שה־RLS מופעל בשתי טבלאות anafim_vault_*, ושה־RPCs מוגבלים למשתמשים מאומתים.
  4. הסקריפט כולל גם restrictive policies, כדי שמדיניות Storage רחבה של bucket אחר לא תחשוף את ה־bucket הפרטי. אל תסירו את המדיניות הזו.
  5. העתיקו את Project URL ואת מפתח ה־publishable או anon הציבורי. אלה הגדרות ציבוריות, לא מפתחות הצפנה.

לעולם לא להכניס לדפדפן או למשתנה VITE מפתח service_role, מפתח sb_secret_, Google Client Secret או סיסמת משתמש. היישום מסרב לשמור מפתחות שרת, ותהליך הבנייה מסרב לארוז מפתח שרת שהוזן כמשתנה הציבורי.

3. Google OAuth

  1. צרו Google Cloud project והגדירו את Branding / Audience / Data Access ב־Google Auth Platform.
  2. צרו OAuth Client מסוג Web application.
  3. ב־Authorized JavaScript origins הוסיפו את מקור האתר, לדוגמה https://family.example.com. לפיתוח אפשר להוסיף http://localhost:5173.
  4. ב־Authorized redirect URIs הוסיפו את כתובת ה־callback של Supabase, שמוצגת בדף Google Provider. בדרך כלל זו https://PROJECT.supabase.co/auth/v1/callback.
  5. ב־Supabase → Authentication → Providers → Google הזינו את Client ID ואת Client Secret רק בלוח הבקרה של Supabase והפעילו את הספק.
  6. ב־Supabase → Authentication → URL Configuration הגדירו Site URL ואת כתובות החזרה המדויקות של האתר. הימנעו מ־wildcard רחב בייצור.
  7. נדרשות הרשאות זיהוי openid, email ו־profile בלבד. אין צורך ב־Google Drive, אנשי קשר או גישה למסמכי המשתמש.
  8. במצב Google Testing הוסיפו חשבונות בדיקה מורשים. פרסום לציבור ואימות מותג כפופים לדרישות Google.
  9. השביתו ספקי התחברות שאינכם מתכוונים להציע, ובדקו מדיניות קישור חשבונות והגבלות קצב לפני ייצור.

אין למסור את ה־Client Secret למשתמשים או לשמור אותו בקוד המקור.

4. הגדרות האתר — שתי דרכים

בנייה מהמקור

העתיקו .env.example ל־.env.local ומלאו רק:

VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR-PUBLIC-PUBLISHABLE-OR-ANON-KEY

הריצו:

npm ci
npm run build

העלו את תוכן dist למארח סטטי ב־HTTPS. המשתנים הציבוריים נכנסים לחבילה בזמן הבנייה; משתמשי האתר אינם צריכים להקליד אותם בכל מכשיר.

חבילת אתר מוכנה, ללא Node

חלצו את anafim-web-2.0.1.zip. ב־index.html ערכו רק את בלוק ההגדרות הציבוריות:

<script id="anafim-cloud-config" type="application/json">
{"url":"https://YOUR-PROJECT.supabase.co","key":"YOUR-PUBLIC-KEY"}
</script>

העלו את כל התיקייה, כולל assets, fonts, favicon ו־_headers, לשורש אתר HTTPS. ה־HTML הזה משתמש בקובצי JavaScript חיצוניים מאותו אתר ומתאים ל־CSP המצורף. קובץ ה־HTML העצמאי להורדה כולל JavaScript פנימי ומיועד בעיקר לתצוגה מקומית; אין להשתמש בו במקום חבילת האתר תחת CSP שחוסם קוד פנימי.

לבדיקה נקודתית ניתן גם לפתוח ״חשבון וענן״ ולהזין את ההגדרות הציבוריות במסך. אפשרות זו נשמרת בדפדפן המסוים; בייצור עדיף להטמיע הגדרות באתר לכל המשתמשים. סדר העדיפות: משתני build, בלוק JSON באתר, הגדרה מקומית.

5. כותרות אבטחה

public/_headers מתאים למארחים שתומכים בפורמט כגון Netlify. במארח אחר העתיקו את הכותרות להגדרות השרת. ברירת המחדל מתירה חיבור ל־*.supabase.co בלבד. אם אתם משתמשים בדומיין Supabase מותאם אישית, עדכנו גם את connect-src לכתובות HTTPS/WSS המדויקות שלו.

אין CDN של JavaScript, סקריפט אנליטיקה או גופנים חיצוניים בזמן ריצה. אל תוסיפו סקריפטים לא מבוקרים לאותו origin: כשהכספת פתוחה, קוד באותו origin יכול להגיע לנתונים המפוענחים. אל תאפשרו framing של גרסת הייצור ללא מדיניות WebAuthn ואבטחה מתאימה.

6. שימוש ושחזור

  1. המשתמש מתחבר עם Google.
  2. בהפעלה ראשונה הוא יוצר Passkey תומך PRF. לא כל דפדפן, מנהל סיסמאות או מפתח חומרה מספק PRF; הבדיקה מתבצעת בפועל, ואין הורדה שקטה ברמת ההצפנה.
  3. המשתמש שומר את מפתח השחזור ומאשר את שמונת תווי הביקורת האחרונים לפני שהכספת נשמרת.
  4. ניתן ליצור כספת ריקה ואז לפתוח קובץ GEDCOM. נתוני משפחת ההדגמה אינם מגובים.
  5. מפעילים במפורש את ״סנכרון אוטומטי״ כל עוד הכספת פתוחה, או שומרים ידנית.
  6. במכשיר אחר נכנסים לאותו חשבון ופותחים ב־Passkey מסונכרן/תואם, או במפתח השחזור. לאחר שחזור אפשר לרשום Passkey נוסף במכשיר תומך.
  7. אם יש גם אילן מקומי וגם אילן בענן, המשתמש בוחר איזה עותק לפתוח או לשמור. אין מיזוג אוטומטי של GEDCOM ואין דריסה שקטה של גרסה חדשה יותר.

Google Password Manager יכול לסנכרן Passkeys בין סביבות תומכות, אך מעבר בין מנהלי סיסמאות או דומיינים אינו מבטיח את אותו credential. שמרו תמיד מפתח שחזור נפרד. לא ניתן להפיק מחדש את מפתח הפענוח ממזהה Google, מאימייל או מאיפוס חשבון.

7. סנכרון, גרסאות ותפעול

  • נשמר קובץ אילן אחד לכל חשבון, עם גרסאות קודמות מוצפנות. אין עריכה משותפת או שיתוף בין חשבונות בגרסה זו.
  • האובייקט המוצפן מועלה בשם UUID חדש; רק אחר כך RPC מחליף את מצביע הגרסה באופן אטומי, בתנאי שהגרסה הקודמת עדיין תואמת.
  • ניתוק רשת אינו גורם למחיקת אובייקט שה־commit שלו אולי הצליח. ייתכנו אובייקטים מוצפנים יתומים לאחר כשל עמום; ניקוי תפעולי חייב לבדוק קודם שהם אינם מופיעים בגרסאות.
  • Realtime משמש לעדכון; יש גם בדיקה כל 20 שניות ובחזרה לרשת/לחלון. סנכרון נפסק כשהכספת נעולה.
  • האילן ושם הקובץ, לרבות מזהה האדם שנבחר לשמירה, נכללים בתוך המטען המוצפן. אין חיפוש או פענוח בשרת.
  • עשר הגרסאות האחרונות מוצגות ביישום, אך לא מתבצעת מחיקה אוטומטית של גרסאות ישנות. הגדירו תקציב, ניטור אחסון ומדיניות שימור מודעת לפני פרסום.
  • כל אובייקט מוגבל ל־50MB מוצפנים; מופעל gzip לפני ההצפנה כשנתמך, ותוכן מפוענח מוגבל ל־96MB. מגבלת הייבוא המקומית נשארת 30MB. בדקו גם את מגבלות/עלויות תוכנית Supabase שבחרתם.
  • ״נעילה״ מסירה את המפתח מהפניות היישום וסוגרת את האילן. נעילה אוטומטית אחרי 10 דקות ללא פעילות. JavaScript אינו מבטיח מחיקה פיזית של זיכרון תהליך.
  • session ההתחברות של Supabase עשוי להישמר בדפדפן, אך מפתח הפענוח אינו נשמר בו. זכירת קובץ מקומית היא אפשרות נפרדת שמסומנת במפורש כלא מוצפנת, וכבויה כברירת מחדל.
  • ״מחיקת כספת״ מוחקת מטא־דאטה וגרסאות ויוזמת מחיקת קובצי ciphertext של המשתמש. כשל חלקי במחיקת אובייקטים מחייב טיפול/ניסיון נוסף בלוח הבקרה. הוא אינו מוחק את חשבון Google/Supabase, עותקים שכבר הורדו או גיבויים של הספק.

8. בדיקות לפני פתיחה לציבור

  • התחברות Google אמיתית, חזרה מדויקת לכתובת האתר ויציאה.
  • לפחות שני חשבונות שונים: האחד אינו יכול לקרוא, לכתוב, לעדכן או למחוק את הנתונים של האחר.
  • שני מכשירים אמיתיים, כולל הדפדפנים ומנהלי הסיסמאות שבהם קהל היעד משתמש.
  • מחיקת/אובדן Passkey ושחזור באמצעות המפתח הפרטי; פתיחה בדומיין הקבוע.
  • כתיבה מתחרה, כשל רשת, חזרה לרשת וטעינה של גרסה קודמת ללא דריסה.
  • אין שמות אנשים, שמות קבצים או מפתחות שחזור ביומני בקשות/מסד/Storage.
  • בדיקת CSP במארח האמיתי וסקירת אבטחה עצמאית לפני שמירת נתונים רגישים של משתמשים אמיתיים.

הבדיקות המצורפות מכסות Web Crypto, PRF אמיתי של Chromium מול authenticator וירטואלי, זרימת OAuth/PKCE מול שירות בדיקה, סנכרון מול ממשק ענן מדומה ו־RLS אמיתי במנוע PostgreSQL מקומי. זו אינה בדיקת Google/Supabase חיה או ביקורת אבטחה עצמאית.
